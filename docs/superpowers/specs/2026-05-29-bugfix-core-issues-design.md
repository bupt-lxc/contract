# Design: Core Bug Fixes — Operations, ID Generation, Filtering, Notifications

Date: 2026-05-29
Branch: `fix/core-issues`

## Context & Scope

The desktop app (Python 3.11 + pywebview + SQLite, Vue 3 frontend) has five categories of bugs that prevent normal usage. All are fixed in a single branch because the fixes overlap (e.g., fixing operations and ID generation both touch the same forms and composables).

Architecture constraint: each user runs their own Python backend process, with a shared-folder SQLite database and file-based lease locks for concurrency control. IDs must be generated with this in mind.

## Section 1: API Payload Standardization

### Problem

Frontend composables send inconsistent payload shapes to the bridge. Several methods are broken:

- `useSc.submitSc(data)` sends `{data}` but bridge expects `{sc_id, data}` — sc_id is inside data, not top-level
- `useSc.updateSc(data)` sends `{data}` but bridge expects `{sc_id, data}`
- `usePo.updatePo(data)` sends `{data}` but bridge expects `{po_id, data}`
- `useGr.updateGr(data)` sends `{data}` but bridge expects `{gr_id, data}`
- `useGr.approveGr(grId)` sends `{gr_id}` but bridge expects `{gr_id, con_value}` — con_value is missing

### Design

Standardize all API calls to match the bridge's expected payload shape:

| Method type | Payload shape | Example |
|---|---|---|
| Create | `{data}` | `create_sc_draft({data: {...}})` |
| Update | `{entity_id, data}` | `update_sc({sc_id: "...", data: {...}})` |
| Action | `{entity_id}` | `approve_sc({sc_id: "..."})` |
| approve_gr | `{gr_id, con_value}` | `approve_gr({gr_id: "...", con_value: 123.45})` |

### Changes

**Frontend composables** (useSc.js, usePo.js, useGr.js):
- `submitSc(scId, data)` → `callApi('submit_sc', {sc_id: scId, data})`
- `updateSc(scId, data)` → `callApi('update_sc', {sc_id: scId, data})`
- `updatePo(poId, data)` → `callApi('update_po', {po_id: poId, data})`
- `updateGr(grId, data)` → `callApi('update_gr', {gr_id: grId, data})`
- `approveGr(grId, conValue)` → `callApi('approve_gr', {gr_id: grId, con_value: conValue})`

**Frontend views** (ScListView.vue, ScDetailView.vue, PoDetailView.vue):
- Update all call sites to pass IDs as separate arguments
- `ScDetailView.handleSubmit()`: pass `scId.value` + empty data (bridge merges with before state)
- `PoDetailView.handleGrApprove()`: prompt for con_value first via `ElMessageBox.prompt`, then call `approveGr(grId, conValue)`

**Backend**: No changes needed. Bridge already has correct expectations.

## Section 2: Auto-Generated IDs

### Problem

Users must manually enter SC ID, PO ID, and GR ID in every create form. These IDs should be auto-generated by the backend.

### Design

**ID format**: `{TYPE}-{MACHINE}-{YYYYMMDD}-{SEQ:03d}`

Examples: `SC-V2SE7PP-20260529-001`, `PO-V2SE7PP-20260529-003`, `GR-V2SE7PP-20260529-001`

**Why machine prefix**: Each user runs their own Python backend. Using machine_id as a prefix guarantees uniqueness across users without cross-machine coordination. Each machine tracks its own daily sequence.

### Changes

**Backend — new `_generate_id()` functions** in each service:

```python
def _generate_id(config: AppConfig, prefix: str, machine_id: str) -> str:
    today = datetime.now(timezone.utc).strftime("%Y%m%d")
    pattern = f"{prefix}-{machine_id}-{today}-%"
    with connect(config) as conn:
        row = conn.execute(
            f"SELECT {prefix.lower()}_id FROM {TABLE} "
            f"WHERE {prefix.lower()}_id LIKE ? "
            f"ORDER BY {prefix.lower()}_id DESC LIMIT 1",
            (pattern,),
        ).fetchone()
    if row:
        last_seq = int(row[0].rsplit("-", 1)[-1])
        seq = last_seq + 1
    else:
        seq = 1
    return f"{prefix}-{machine_id}-{today}-{seq:03d}"
```

- `sc_service.create_sc_draft()`: generate sc_id, remove from required fields
- `po_service.create_po()`: generate po_id, remove from REQUIRED_FIELDS
- `gr_service.create_gr()`: generate gr_id, remove from REQUIRED_FIELDS

**Frontend**:
- `ScFormDialog.vue`: remove SC ID input field
- `PoFormDialog.vue`: remove PO ID input field
- `GrFormDialog.vue`: remove GR ID input field
- All forms: remove ID from `rules` and `emptyForm()`

## Section 3: Form Required Field Alignment

### Problem

Frontend form rules show fewer required fields than the backend actually requires. Users see a field as optional, fill it in partially, and get a server-side error on submit.

### Design

**SC form** (ScFormDialog.vue):

| Action | Required fields (frontend rules) |
|---|---|
| Save Draft | `requester_id` |
| Submit | `requester_id`, `request_type`, `cost_center`, `sc_amount`, `service_period_start`, `service_period_end` |

**PO form** (PoFormDialog.vue):

| Action | Required fields |
|---|---|
| Save | `vendor_id`, `po_amount` |

**GR form** (GrFormDialog.vue):

| Action | Required fields |
|---|---|
| Save | `requester_id`, `estimated_amount` |

### Changes

**Frontend forms**: Each form defines two rule sets (`draftRules` / `submitRules`). The submit button uses `submitRules` for validation, the draft button uses `draftRules`. Every required field gets a red asterisk (`required: true` in el-form rules).

## Section 4: Query Filter Enhancement

### Problem

List views offer only 2-3 filter fields. The backend supports many more `allowed_filters` and full-text search, but the frontend doesn't expose them. Date filters use exact match (`=`) which is useless for dates.

### Design

**4a. Backend: Complete allowed_filters**

Add all remaining table columns to `allowed_filters` and `text_columns` in `query_service.py`:

sc_records additions: `sc_amount`, `service_period_start`, `service_period_end`, `description`, `created_at`, `updated_at`, `approved_by`, `approved_at`, `closed_at`

pos additions: `po_amount`, `contract_from`, `contract_to`, `contract_no`, `payment_frequency`, `created_at`, `updated_at`

gr_requests additions: `estimated_amount`, `con_value`, `remark`, `created_by`, `created_at`, `approved_by`, `approved_at`, `cancelled_by`, `cancelled_at`

vendors additions: `contact_person`, `email`, `phone`, `description`, `status`, `created_at`, `updated_at`

**4b. Backend: Range filter support**

Extend `_append_filters()` to recognize suffix operators on filter keys:

| Suffix | SQL operator |
|---|---|
| `_from` | `>=` |
| `_to` | `<=` |
| `_min` | `>=` |
| `_max` | `<=` |
| (no suffix) | `=` |

Register range variants in `allowed_filters`, e.g.:
```python
"service_period_start_from": "sc.service_period_start",
"service_period_start_to": "sc.service_period_start",
"sc_amount_min": "sc.sc_amount",
"sc_amount_max": "sc.sc_amount",
```

**4c. Frontend: AdvancedFilterBar component**

Replace `FilterBar.vue` with a new `AdvancedFilterBar.vue`:

- Always-visible text search input (searches backend `text_columns`) with 500ms debounce
- Expandable "Advanced Filters" section with all filter fields for that page
- Receives a `filterConfig` prop defining each field: name, label, control type (`select`, `input`, `date-range`, `amount-range`)
- Date fields render as date picker with range support → emits `field_from` / `field_to` filters
- Amount fields render as min/max input-number pair → emits `field_min` / `field_max` filters

**Per-page filter fields** (all exposed):

| Page | Filter fields |
|---|---|
| SC List | sc_id, sc_no, requester_id, request_type, cost_center, status, created_by, service_period_start(_from/_to), sc_amount(_min/_max) |
| PO List | po_id, po_no, sc_id, vendor_id, status, vendor_name, po_amount(_min/_max), contract_from(_from/_to), contract_to(_from/_to) |
| GR List | gr_id, po_id, requester_id, status, sc_id, vendor_id, estimated_amount(_min/_max), con_value(_min/_max) |
| Vendor List | vendor_id, vendor_name, ksrm_vendor_code, service_scope, created_by, contact_person, email, status |
| Audit Logs | action_type, object_type, object_id, sc_id, operator_id, machine_id, operation_mode |

## Section 5: Notification Multi-Select Fix

### Problem

The email notification configuration's multi-select components (`el-select multiple` for CC lists, `el-checkbox-group` for thresholds) are reported as non-functional — selections don't register.

### Design

Primary fix: Add `:teleported="false"` to all `el-select` components with `multiple` attribute. In pywebview's embedded browser, the default teleport-to-body behavior can misplace or hide the dropdown.

Secondary fix: Ensure the reactivity chain (`@change` → `emitSave` → API call → `state.scConfig` update → watch → local reset) doesn't accidentally overwrite user selections. Verify the data round-trip shape is consistent.

### Changes

- `ScNotificationCard.vue`: add `:teleported="false"` to el-select, verify reactivity
- `NotificationDefaults.vue`: add `:teleported="false"` to all 6 el-select instances, verify reactivity

## Section 6: Approve GR con_value Input

### Problem

When a user clicks "Approve" on a GR, `useGr.approveGr(grId)` sends only `{gr_id}` but the bridge requires `{gr_id, con_value}`. There is no UI to enter the contract value.

### Design

Before calling the approve API, show `ElMessageBox.prompt` asking for the contract value (con_value). Validate it's a positive number, then call `approveGr(grId, conValue)`.

### Changes

- `PoDetailView.vue` / `handleGrApprove()`: add prompt dialog
- `useGr.js`: update `approveGr(grId, conValue)` signature
